# План реализации очереди

Основание: уточнённый пользовательский сценарий. Очередь автоматически формируется после подтверждённого допуска; посещение конкретного занятия по умолчанию выключено. Текущий этап — начало реализации, а не готовая интеграция.

## Найденные точки подключения

- `frontend/courses-front/src/components/registration-form/index.jsx`: существующая форма ФИО и GitHub, последовательные запросы регистрации и проверки.
- `main.py`: `grade_lab`, запрос `/courses/{course_id}/groups/{group_id}/labs/{lab_id}/grade`; результат готовится через `grading.bulk.evaluate_student`.
- `grading/sheets_client.py`: чтение и разбор дедлайнов уже существуют; доступен разбор из загруженного массива ячеек.
- `frontend/courses-front/src/components/admin/`: существующая авторизация и раздел преподавателя.
- Старые отдельные `grading/priority_queue.py` и связанные незакоммиченные файлы не подключены. Новая реализация находится в `grading/defense_queue/`.

## Сценарий интерфейса студента

На существующей странице появляются вкладки «Регистрация» и «Список на занятие». В заголовке списка: предмет, группа, дата/время и режим очереди. Список загружается независимо от долгого запроса проверки.

Во время проверки предполагаемая строка студента подсвечивается только в его браузере и помечается «предварительная позиция». Она не резервирует место и не даёт допуск другим запросам. Положение может измениться после проверки и действий других студентов.

После подтверждённого допуска участник сохраняется в постоянной очереди. Без ответа строка полупрозрачная, посещение выключено. «Да, я приду» включает в состав и делает строку обычной; явное «Нет» зачёркивает. Различие «ещё не отвечал / отказался» сохраняется отдельным полем.

Управление посещением доступно при повторном открытии страницы. Для уже допущенной работы не требуется запускать проверку заново. До начала пары ответ изменяется в обе стороны; после начала действия относятся к следующему занятию. Вызванный преподавателем студент не перемещается из-за новых записей.

Обновления списка сначала выполняются коротким опросом API, например раз в 5 секунд с остановкой при скрытой вкладке. WebSocket для первой версии не требуется. Ошибка обновления показывает последнее подтверждённое состояние и сообщение, не очищает список.

## Настройки и данные

Случайный режим обязателен и заблокирован, если данные сроков получить не удалось и ручного значения нет. Явное отсутствие срока является корректным состоянием и не отключает −1; такая работа располагается после работ с заданными сроками, без подстановки приоритета 0. При восстановлении данных по умолчанию включается −1; преподаватель может выбрать случайный режим. Частичная ошибка получения сроков переводит состав в случайный режим; частичное отсутствие сроков по правилам работ этого не делает. Случайные ключи сохраняются в БД и не создаются при каждом чтении списка.

Постоянный участник не равнозначен посещению пары. Завершённая попытка не перезаписывается новой. Источник допуска — серверная проверка и прочитанная таблица; клиентское сообщение об успехе не является основанием добавления.

Сверка через 10 минут должна переживать перезапуск: время выполнения и результат записываются в SQLite. Получение таблицы выполняется вне транзакции. Автоматическое исчезновение `vv` не отменяет уже подтверждённую защиту без отдельного правила. Конфликт результата кнопки и таблицы требует решения до реализации этой ветки.

## Уточнения команды

1. Сложный механизм конфликтов не требуется: оба результата задаёт преподаватель; повторная сверка не дублирует результат.
2. Отсутствие срока и недоступность данных различаются; приоритет 0 для отсутствующего срока не используется.
3. Идентификация остаётся через существующую форму.
4. После «не сдал» повторная попытка добавляется в конец и визуально выделяется.
5. По предоставленному образцу уточнить ячейки сроков и обозначения защиты; формат таблицы не менять.

## Реализованный разбор таблицы

`grading/defense_queue/sheet_state.py` разбирает допуск и защиту, баллы/штрафы, порядок обязательных работ и источник дедлайна. Для срока есть явное состояние «без дедлайна»; пустая ячейка сама по себе не доказывает отсутствие срока по правилам работы. Ручной срок перекрывает ошибку чтения. Проверено шестью тестами. Сетевое чтение таблицы и подключение к HTTP-обработчикам остаются следующим этапом.

## Подключение к приложению

Добавлены синхронизация полной прочитанной таблицы, hook после существующего `grade_lab`, маршруты чтения списка/изменения посещения и защищённый маршрут ручного создания занятия. Снимок начавшейся пары сохраняется в SQLite; последующее чтение `vv` не удаляет его строки. Порядок и посещение проверены на временной базе; HTTP-запуск ожидает backend-зависимостей. Инструкция: [API.md](API.md). Панель преподавателя, студенческий интерфейс и отложенная сверка пока не подключены.
