# ADR-0002. Состояние очереди и история в SQLite

Храним занятия, записи и события в одной локальной SQLite-базе на постоянном диске. Каждое действие меняет запись и добавляет событие одной транзакцией. Это сохраняет очередь при перезапуске и позволяет объяснить её состояние без отдельного серверного сервиса БД.

## Контекст и границы

Очередь должна переживать перезапуск процесса и обновление приложения. Несколько студентов могут нажать «записаться» одновременно, а преподаватель может открыть страницу в двух вкладках. Одного списка в памяти недостаточно: теряются ожидающие, результаты и защита от дублей.

Курсов, групп и занятий несколько. Их время может пересекаться. Имя студента не уникально, GitHub может быть ещё не сопоставлен, а строка в Google Sheets может переместиться. История должна содержать отдельные попытки, а не только последнее состояние студента.

Встроенная БД допускается предоставленными разъяснениями задания при обосновании усложнения. SQLite не требует отдельного сетевого сервиса. Все записи относятся к организации защит; оценки остаются в существующих таблицах и не обновляются этим модулем.

## Рассмотренные варианты

| Вариант | Сохранность | Конкурентные изменения | Цена для проекта | Вывод |
|---|---|---|---|---|
| Список в памяти | Теряется при остановке | Нужны блокировки, между процессами состояние расходится | Минимум для демонстрации | Не удовлетворяет хранению истории |
| JSON на диске | Возможна при корректной атомарной замене | Требуются отдельные блокировки и защита от потерянных обновлений | Растёт с появлением истории и ограничений | Прост только до появления нескольких писателей |
| Google Sheets как очередь | Внешнее постоянное хранение | Нет общей транзакции со своим состоянием и привычных SQL-ограничений | API-запросы, лимиты, сеть, риск задеть оценки | Оставляем источником допуска, без записи состояния очереди |
| SQLite | Локальные транзакции и ограничения | Один писатель; короткие операции сериализуются | `sqlite3` в стандартной библиотеке, один файл и миграции | Выбрано |
| PostgreSQL | Серверные транзакции и больше возможностей параллельной записи | Подходит для нескольких хостов | Отдельное развёртывание и эксплуатация | Избыточно для текущего масштаба и ограничения внешних сервисов |

SQLite подходит для приложения на одном хосте с умеренным числом коротких записей; документация отдельно рассматривает такой тип применения. Это соответствие предполагаемой нагрузке, а не проведённый нагрузочный тест. [SQLite: Appropriate Uses](https://sqlite.org/whentouse.html).

## Решение и структура

Полная DDL находится в [schema.sql](../queue/schema.sql), пояснения полей и операции в [структуре БД](../queue/README.md). Файл является исполняемой спецификацией и проверен на временных базах; приложение его пока не применяет.

```mermaid
erDiagram
    courses ||--o{ study_groups : includes
    courses ||--o{ course_students : enrolls
    students ||--o{ course_students : studies
    study_groups ||--o{ course_students : contains
    study_groups ||--o{ sessions : holds
    study_groups ||--o{ schedule_overrides : changes
    sessions ||--o{ queue_entries : has
    students ||--o{ queue_entries : attempts
    sessions ||--o{ queue_events : records
    queue_entries o|--o{ queue_events : explains
```

| Таблица | Назначение |
|---|---|
| `courses` | Стабильный `course_id` из индекса конфигурации, часовой пояс, источник расписания и окно записи |
| `study_groups` | Группы внутри курса; одинаковое обозначение группы на разных курсах не смешивает данные |
| `students` | Внутренний идентификатор, ФИО и необязательный GitHub. ФИО не является ключом |
| `course_students` | Актуальное соответствие студента курсу, группе и стабильному ключу строки источника |
| `schedule_overrides` | Отмена дня для группы или дополнительное занятие; автор и ревизия изменения |
| `sessions` | Конкретное занятие/дневная сессия, временные границы и назначенный преподаватель |
| `queue_entries` | Одна попытка защиты одной работы: состояние, приоритет, время и снимок данных для истории |
| `queue_events` | Неизменяемая история записи и занятия с автором действия |

Двух таблиц «студент + очередь» не хватает для нескольких попыток одного человека и нескольких занятий одной группы. Если записать результат и время прямо в строку студента, новая защита перезапишет предыдущую. Если хранить один общий список, пересекающиеся пары смешаются. Отдельной таблицы `queues` не нужно: очередь является упорядоченными активными записями конкретного `session_id`.

Не создаём копию всех курсовых оценок или реестр лабораторных. `lab_key` и `lab_order` проверяются по конфигурации курса. `eligibility_snapshot` хранит прочитанное обозначение допуска и время чтения для объяснения решения; это не новая оценка. Снимки ФИО и GitHub сохраняют вид истории при последующем исправлении профиля. Стабильный ключ источника нельзя подменять номером строки Sheets. При отсутствии однозначного сопоставления записываться от имени первого совпавшего ФИО нельзя: интерфейс должен запросить уточнение по существующему контексту группы/GitHub.

Курс и студенты не удаляются каскадом вместе с историей. Перевод в другую группу меняет текущее членство, старые записи сохраняют свою группу и снимки. Записи не ссылаются на изменяемое членство через составной FK; его актуальность проверяется при новой записи, а принадлежность записи занятию закреплена составным внешним ключом.

## Целостность и одновременные запросы

На каждом соединении включаем `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=FULL`. Для базы на локальном постоянном диске выбираем `journal_mode=WAL`: читатели могут работать параллельно с писателем, но одновременно писать всё ещё может один процесс. Сетевой том для общего WAL между хостами не подходит. [SQLite WAL](https://sqlite.org/wal.html).

Внешние ключи надо включать для **каждого** соединения; одной установки при создании файла недостаточно. [SQLite Foreign Keys](https://sqlite.org/foreignkeys.html).

Ограничения DDL:

- Одна активная (`waiting` или `called`) запись студента **на курс**, даже если окна двух занятий этого курса пересекаются.
- Один вызванный студент на `teacher_key` сразу для всех занятий и курсов преподавателя. Другой преподаватель может принимать параллельно.
- Группа, курс и преподаватель записи совпадают с занятием через составной FK.
- Одинаковый `request_key` не создаёт вторую запись при повторном HTTP-запросе.
- Закрытая запись имеет `closed_at`, вызванная имеет `called_at`, значения состояния и диапазоны полей ограничены.
- События нельзя обновлять или удалять обычными SQL-операциями; событие записи относится к тому же занятию.

Подготовка данных из Sheets и расписания идёт **до** короткой транзакции. В `BEGIN IMMEDIATE` повторно проверяем окно записи по серверному времени, состояние занятия, актуальность подготовленного допуска и отсутствие активной записи; создаём запись и событие, выполняем `COMMIT`. При исключении откатываем оба. Нельзя держать блокировку БД во время сетевого запроса. Если свежий допуск получить не удалось, новая запись отклоняется с возможностью повторить, существующие записи и история доступны.

Снимок допуска фиксирует уже прочитанные сведения, но не обеспечивает распределённую транзакцию с Google Sheets. Перед новой записью читаем актуальное состояние; для отдельного вызова можно повторить проверку и показать конфликт преподавателю. Не обещаем, что внешняя ячейка никогда не изменится между чтением и подтверждением.

При вызове следующего используем `BEGIN IMMEDIATE`, проверяем, что преподаватель не принимает другого студента, выбираем первого ожидающего и делаем `UPDATE ... WHERE status='waiting' AND version=?`. Ровно одна изменённая строка означает успешный вызов; иначе возвращаем конфликт и обновляем экран. Затем пишем событие и фиксируем транзакцию. `version` и частичный уникальный индекс защищают от двух вкладок.

`request_key` создаётся клиентом на одно намерение и повторно используется при сетевом повторе. Сервер хранит его глобальную уникальность, сверяет владельца и параметры исходного запроса и возвращает уже созданную запись только тому же участнику. Совпавший ключ с другим содержимым вызывает конфликт. `request_key` не является средством авторизации.

Схема не заменяет серверные проверки: членство в группе, окно записи, выбор первой обязательной работы, допустимые переходы статусов, полномочия преподавателя, запрет записи без собственного подтверждения и согласованность кэша проверяются прикладным кодом. Тесты БД не являются тестами ещё не написанного API.

## История и восстановление

`queue_entries` хранит текущее состояние, `queue_events` объясняет последовательность действий. Это обычная таблица состояния с журналом, а не полноценная система event sourcing: автоматическое восстановление любой версии состояния из журнала в первую версию не входит.

Результаты преподавателя: `defended`, `failed`, `no_show`. Самостоятельный выход: `withdrawn`. Истечение конца дня: `expired`, **не** `no_show`. Завершённую запись не переписываем для повторной попытки, создаём новую. Ошибку преподавателя исправляем отдельным событием с причиной и контролируемым изменением; автоматического восстановления права на следующую работу без согласования не делаем.

На запуске выполняем миграции и закрытие просроченных записей. Те же проверки работают при чтении и изменении очереди, чтобы окончание дня не зависело от фонового таймера. `expires_at` хранится как конкретный момент конца местного дня; история не исчезает после перезапуска. Ожидающие вчера не становятся автоматически ожидающими сегодня.

## Развёртывание и копии

Предполагаемый путь задаётся `QUEUE_DB_PATH`, например `/app/data/queue.sqlite3`. Каталог монтируется как постоянный локальный том и доступен только приложению и администратору. Без постоянного тома удаление контейнера уничтожит локальную БД независимо от транзакций. Это требование будущего деплоя, сейчас compose и окружение не менялись.

Миграции версионируем через `PRAGMA user_version`, применяем один раз под транзакцией перед обработкой запросов. При несовместимой версии запуск завершается с понятной ошибкой. Перед изменением схемы делаем резервную копию; миграция нескольких одновременно стартующих процессов требует общего контроля версии под блокировкой.

Резервные копии выполняются через `sqlite3.Connection.backup()` на отдельный носитель/каталог с ограниченным доступом; копирование только основного файла работающей WAL-базы не используется как процедура бэкапа. Для восстановления проверяем `integrity_check` и пробное чтение истории. [SQLite Online Backup](https://sqlite.org/backup.html).

База не даёт обещания «данные сохраняются всегда»: потеря диска, удаление тома или отсутствие бэкапа остаются рисками. Для первой версии нужны ежедневная копия и копия перед миграцией; целевой допустимый объём потери данных равен периоду между успешными копиями. Срок хранения истории согласуется с курсом; в Git не попадают рабочие `.sqlite3`, `-wal`, `-shm`, реальные ФИО, ключи допуска и бэкапы. В этом пакете есть только DDL и синтетические тесты.

## Почему усложнение оправдано

Транзакция и два уникальных индекса решают конкретные ошибки: двойную запись, двух одновременно вызванных студентов и потерю события при сбое. Реализовывать те же гарантии вокруг JSON означало бы писать блокировки и протокол восстановления вручную. При этом не добавляются сервер БД, очередь сообщений или отдельный воркер.

Пересмотр решения нужен при нескольких хостах приложения, регулярных `SQLITE_BUSY` после коротких транзакций или требовании высокой параллельной записи. Тогда оцениваем серверную СУБД; сам факт нескольких групп или пересекающихся пар перехода не требует. Численные пределы нагрузки пока не измерены.

## Что проверено

Запуск [test_schema.py](../queue/test_schema.py) создаёт временные файлы. Проверены: повторное открытие с сохранёнными данными; конкурентная запись из двух соединений; одна активная запись на курс; границы групп; один вызов на преподавателя; повторная запись в конце; атомарный откат записи с событием; неизменяемость истории; резервная копия с зафиксированными WAL-данными; сохранение ожидающих при отмене записи на занятие. Это проверка проекта схемы, без нагрузки на работающий сервис и без изменения Google Sheets.
