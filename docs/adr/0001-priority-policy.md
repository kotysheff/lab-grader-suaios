# ADR-0001. Нижняя граница приоритета −1

Команда выбирает очередь, в которой просроченные работы имеют приоритет −1, работы с текущим дедлайном 0, а будущие дедлайны положительны. Увеличение просрочки не даёт дополнительного преимущества. Исследование не подтверждает, что этот выбор максимизирует долю оценок 4–5: в базовом эксперименте по этому критерию лучше граница 0.

## Контекст

На занятии ограничен ресурс преподавателя. Случайный порядок не учитывает близость срока, а неограниченное предпочтение самых старых работ может вытеснять студентов, ещё способных сдать больше работ без штрафов. Нужен порядок, который можно объяснить студенту и восстановить по истории.

Команда первоначально выбрала основной KPI: доля итоговых оценок 4–5. Полные результаты, точные параметры, исходники, сырые баллы, графики и доверительные интервалы сохранены в [исследовании](../../research/queue-study/README.md). Сравнивались все предоставленные AllModels, а отдельно случайная очередь и нижние границы 0 и −1 при изменении вместимости, посещаемости, сроков и других допущений.

Выбор приоритета определяет порядок обслуживания. Он не заменяет условия допуска, самостоятельное подтверждение записи студентом, расписание и ограничение одной активной записи на курс.

## Решение

Для каждой первой записи студента в текущий учебный день рассчитываем:

```text
delta_weeks = deadline_week - session_week
priority = max(-1, delta_weeks)
```

`deadline_week` и `session_week` являются номерами учебных недель относительно `semester_week_anchor` из конфигурации курса. Номер недели вычисляется по местной календарной дате: `1 + (date - anchor_date).days // 7`. `session_week` определяется началом занятия и одинаков для всех его записей. Часовой пояс берётся из курса; недели не вычисляются делением секунд UTC, чтобы смена часового пояса не сдвигала календарные границы. Для этой политики работа с дедлайном в текущую учебную неделю имеет 0; со следующей недели она имеет −1. Это недельная политика, а не сортировка по часам до срока. На приёмке проверяем сопоставление реальных дат дедлайнов курса и учебных недель.

Примеры при разнице, заданной целым числом недель:

| До дедлайна | Приоритет | Порядок |
|---|---:|---|
| Просрочка 10 недель | −1 | Один класс со всеми просроченными |
| Просрочка 1 неделя | −1 | Раньше текущего дедлайна |
| Текущий дедлайн | 0 | После просроченных, перед будущими |
| Осталось 2 недели | 2 | После более близких дедлайнов |
| Осталось 18 недель | 18 | Верхнего ограничения нет |

**Важная граница:** внутри одной учебной недели приоритет не меняется из-за наступления следующего дня. В начале следующей недели работа с прошлым дедлайном становится −1. Точная дата дедлайна всё равно сохраняется для объяснения и пересчёта. Штраф за проверку и приоритет не выводятся друг из друга. Если заказчику потребуется различать просрочку внутри недели, это отдельное изменение политики и сценариев, а не незаметная замена формулы.

Начальный порядок: `(priority, entry_id)`; время записи отображается и сохраняется сервером. Монотонный `entry_id` разрешает совпадения времени и не меняет порядок при коррекции системных часов. При изменении дедлайна пересчитываем ожидающие первые записи одной транзакцией с событием `priority_recomputed`. Вызванный студент сохраняет место до результата, а уже закрытые записи хранят прежний приоритет. При обычном ходе занятия приоритет фиксируется на его начало и не меняется каждую секунду.

Выбирается **первая обязательная незащищённая работа по порядку**, а не первая из любых допущенных. Если ЛР1 не защищена и не допущена, готовая ЛР2 не даёт права записаться на неё. После защиты ЛР1 следующей становится ЛР2, если она допущена. Обязательность и порядок берутся из конфигурации курса. История защиты учитывается вместе с прочитанным состоянием таблицы, чтобы задержка обновления `vv` не предлагала снова уже защищённую работу. При конфликте источников показываем причину и разрешаем преподавателю исправить историю отдельным событием, без редактирования оценок.

После завершённого обслуживания студент может записаться снова в пределах открытого окна. Новая запись помечается `is_repeat=1` и добавляется в общий конец, независимо от её приоритета и номера работы. Первая и повторные попытки одной работы являются разными записями с общей историей студента.

Приоритет не даёт повторной попытке обойти людей, уже ожидающих первичную защиту. Среди повторных записей действует порядок их создания, **без сортировки по приоритету**. Новые первые записи занятия остаются в основной приоритетной части перед повторными. Это явное правило команды, которое нужно показать на приёмке: при непрерывном притоке первых записей повторная защита может не успеть. Отмена записи и повторное нажатие кнопки не обнуляют отметку уже состоявшегося обслуживания в этот день. Первая самостоятельная отмена до вызова не считается завершённым обслуживанием; повторное вступление получает новое время записи.

Запрос следующего студента использует:

```sql
SELECT entry_id
FROM queue_entries
WHERE session_id = ? AND status = 'waiting'
ORDER BY is_repeat,
         CASE WHEN is_repeat = 0 THEN priority ELSE 0 END,
         entry_id
LIMIT 1;
```

В DDL `entry_id` монотонно растёт, а `joined_at` задаётся сервером. Поэтому в пределах непрерывной сессии он служит устойчивым порядком создания, даже если системные часы были скорректированы. Импорт старых записей с произвольным порядком не поддерживается без отдельной миграции.

Неявку и результат указывает преподаватель. Самостоятельное подтверждение «приду» не является отметкой о фактической явке. Завершённые статусы: `defended`, `failed`, `no_show`; студент может выйти сам (`withdrawn`); в конце дня оставшиеся записи получают `expired`. После конца пары новые записи закрываются, существующих ожидающих можно принять до конца дня. История не превращается автоматически в активные записи следующего занятия.

## Рассмотренные варианты

| Вариант | Причина решения |
|---|---|
| Случайная очередь | Простой контрольный вариант. В базовом эксперименте заметно уступает обоим ограниченным приоритетам по 4–5; реальное FIFO она не заменяет |
| FIFO по времени записи | Хорошо объясняется, не выделяет близкие сроки. Настоящее FIFO в AllModels отсутствует, поэтому численно побеждённым его не называем |
| Неограниченный приоритет | Очень старая работа получает большее преимущество; модель демонстрирует пользу ограничения снизу, но без гарантии для любых данных |
| Нижняя граница 0 | Лучший из трёх финалистов по основному KPI в базе; при 15 местах преимущество над −1 значительно возрастает |
| Нижняя граница −1 | Выбрана командой ради отдельного класса просроченных работ; измеренная потеря по KPI вынесена на ревью |
| Сначала больше завершённых работ | Много пятёрок сочетается с большой долей нулевых результатов; не подходит как единственное правило |

## Последствия и основание пересмотра

Реализация содержит одну настраиваемую нижнюю границу, а схема хранит результат расчёта и исходный дедлайн. Переключение на 0 не требует менять данные или пересоздавать записи; пересчёт ожидающих должен оставлять событие в истории.

**Если критерием приёмки остаётся исключительно максимизация доли 4–5 при базовых 20 местах, данные поддерживают 0. При 15 местах из трёх финалистов лучше случайный порядок.** Формулировка «−1 лучше всех» не соответствует измерениям. Выбор −1 является заданной политикой команды, а не статистическим выводом. Исследование добавляет к этому выбору новые данные; согласие команды именно с измеренной уступкой пока не подтверждено.

Симуляция использует случайные равные приоритеты и одну попытку в неделю. Продуктовый вариант со стабильным порядком, добровольной записью и повторными попытками за занятие требует собственного тестирования. Допуск из таблицы читается через существующие средства проекта; приоритет вычисляется по сроку работы. Ячейка `v-3` может отражать зафиксированный штраф, а не текущий возраст долга.

Окончательно согласовать с заказчиком нужно сам приоритетный порядок, включая его отличие от обычной записи по времени. Подготовленный ADR не выдаётся за такое согласование.

## Проверка реализации

До подключения к интерфейсу: границы −1/0/+1/+18; сохранение порядка при одинаковом времени; запрет обхода первой обязательной работы; повторная запись с −1 после ожидающего с +18; отсутствие автоматического переноса на завтра; неизменность вызванной записи при пересчёте; двойное нажатие и два параллельных вызова преподавателя. Сейчас проверены вычислительные модели и ограничения [схемы](../queue/schema.sql), а эти сценарии приложения являются критериями следующего этапа.
